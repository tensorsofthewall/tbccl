# TBCCL 0.6.0 validation (draft)

```{warning}
**This is not a certification.** TBCCL 0.6.0 is the first release (package version 0.6.0, C ABI 1, wire protocol 4); it was promoted from release candidate 0.6.0rc1 without runtime changes. This page summarizes the validation evidence for the tree the release was cut from, and lists what the final release still needs. A condensed list of exercised configurations is on the [validated configurations](../project/validated-configurations.md) page.
```

## Scope of the existing evidence

All results below were recorded during development of the wire-protocol-4 tree and are **historical** with respect to a future release candidate. They were not re-run on a tagged release commit.

| Item | Value |
|---|---|
| Version under test | package 0.6.0, public version 0.6.0rc1, C ABI 1, wire protocol 4 |
| Linux host | x86-64, NVIDIA RTX 3070 Ti Laptop GPU, CUDA |
| macOS host | Apple silicon (arm64), Metal shared memory |
| Physical link | direct Thunderbolt 4 cable, TCP over `thunderbolt0` and `bridge0`, MTU 9000 |

## World sizes and operations

World sizes 1 to 4 are validated for the supported operations: byte-generic `send`/`recv`, `broadcast`, `all_gather`, `barrier` and `Sum` `all_reduce` (Float16 and BFloat16 at world size 2 only). Mixed point-to-point and collective traffic was exercised at world sizes 2, 3 and 4. See [Platform capabilities](../reference/platform-capabilities.md).

## Mixed-domain correctness (the wire 4 change)

- Before the change, a Host-only reproducer failed in 30 to 34 of 88 scenarios (protocol errors) and silently corrupted data in large-message scenarios (16 MiB and 64 MiB).
- After the change, an 88-scenario matrix (4 KiB and 1 MiB, same, opposite and mirrored relative order, several families of P2P and collective mixes) passed at three random seeds, and the 22 large-message scenarios (16 MiB and 64 MiB) passed.
- A jitter stress of 1,000 iterations of 4 KiB and 100 of 1 MiB with randomized P2P interleaving passed with exact results; multi-thread submission (including under ThreadSanitizer) passed.
- A CUDA test (45 cases: operation family, size and five variants, with one CUDA rank and one Host rank) passed.
- C ABI: mixed concurrent submission from several threads and an abort test passed; the 28 exported symbols are unchanged.

## Failure handling and lifecycle

Abort, destroy with work in flight, peer death (forked process killed mid-collective), handshake errors in both role orders, a missing data role, duplicate roles, a collective kind mismatch with point-to-point in flight at world size 3, and repeated create/destroy and mixed-traffic cycles (file descriptor and thread counts returned to baseline) all behaved as specified: operations became terminal with the expected structured error, in bounded time, with no leaks. All peer-failure tests are loopback only.

## Wire compatibility

A wire 3 peer dialing a wire 4 rank, and a wire 4 dialer against a wire 3 listener, were both rejected with `protocol_mismatch ... wire protocol`, bounded in time, with nothing but the handshake exchanged. Wire 3 and wire 4 do not interoperate.

## Sanitizers

The mixed-domain, failure, lifecycle and C ABI suites were run under AddressSanitizer with UndefinedBehaviorSanitizer and under ThreadSanitizer on Linux and were clean. Sanitizer coverage of CUDA and Metal device code itself is not claimed.

## C ABI

Layout static assertions and `tests/c_api/` (layout, functional, thread-safety, mixed-domain), the exported-symbol pin (`abi_symbols_v1.txt`) and the pure-C external-consumer build against an installed package.

## CUDA and MPS

CUDA functionality is covered by the CUDA tests above and by torch-tbccl on CUDA tensors. macOS MPS tensors are supported through torch-tbccl (see its documentation); MPS operations from several application threads at once are limited by PyTorch, not by TBCCL.

## Physical Thunderbolt 4 runs

Linux and macOS ranks over the real link, both orientations (Linux rank 0 and macOS rank 0), with link health read before and after: CPU mixed all_reduce plus point-to-point at 4 KiB and 1 MiB in same, opposite and mirrored order; CUDA to MPS mixed traffic; and a CUDA to MPS distributed-data-parallel run of 10 steps with an application thread exchanging 40 deterministic 256 KiB messages on the same group. All passed with exact payloads and no protocol error; the PCIe AER error counters stayed at zero throughout, and no failure was injected on the physical link.

## Known limits recorded

- At world size 2 a collective count or size mismatch is not detected.
- Small-message `all_reduce` latency on loopback is bimodal after the change (negligible next to real-link latencies); it was characterized, not tuned.
- A live pair now holds two more file descriptors and four more threads than before the change.
- Reductions are `Sum` only through `Communicator::all_reduce`; Float16 and BFloat16 reductions need world size 2.

## Release-candidate artifact checks

The published 0.6.0rc1 archives were built by CI from the tagged commit; their checksums, SBOMs and build attestations verify, and the archives that were installed on the test machines are byte-identical to the published ones. Physical Thunderbolt 4 runs between a Linux CUDA host and a Mac, host-memory and CUDA-to-Metal suites in both rank orientations, were repeated with those archives and passed with link health unchanged.

## Not yet done for a 0.6.0 release

- The final release itself: no `v0.6.0` tag, archives or numbered documentation exist yet.
- A security and licensing review (planned separately).

## Release 0.6.0 artifact checks

The 0.6.0 archives were built by CI from the tag `v0.6.0` (commit `29359adc12d0a806db4b659653f8c2470f4a8279`); their `SHA256SUMS` verify and the build attestations verify to that commit. `bin/tbccl-info` of the Linux CUDA archive reports `TBCCL 0.6.0`, package 0.6.0, C ABI 1, wire protocol 4, providers host and CUDA; the macOS archive reports the same with host and Metal-shared providers. The documented install examples (`scripts/check_doc_examples.sh`, `find_package` and the Linux pkg-config path) build and run against the Linux host archive, and the `find_package` path against the Linux CUDA and macOS archives (the pkg-config path with the CUDA archive needs the CUDA runtime added by the caller, as documented; the macOS test host has no pkg-config). Transport over the physical Thunderbolt 4 link was exercised through the final adapter wheels that bundle this release: see the [torch-tbccl](https://torch-tbccl.tensorsofthewall.com/en/stable/validation/0.2.0.html), [vllm-tbccl](https://vllm-tbccl.tensorsofthewall.com/en/stable/validation/0.2.0.html) and [exo-tbccl](https://exo-tbccl.tensorsofthewall.com/en/stable/validation/0.3.0.html) validation pages. The kernel log showed no AER or link events during those runs.
