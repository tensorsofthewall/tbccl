# TBCCL 0.7.0 validation

```{warning}
**This is not a certification.** TBCCL 0.7.0 is a minor release of 0.6.1 (C ABI 1, wire protocol 4, endpoint blob format 1) that runs the two-rank `all_gather` as a concurrent exchange and adds two opt-in tuning settings. This page records the validation of the development tree and of the CI-built artifacts of the release candidate 0.7.0rc1, from which 0.7.0 was promoted without a change to `src/` or `include/`.
```

## What changed since 0.6.1

Seven files under `src/` and `include/` (the communicator, the staging pool and the worker) and the documentation, tests and tools around them. The exported C symbols and the public C header are unchanged. The four changes are: opt-in chunking of staged transfers, a fix for a staged-transfer hang on cancellation, the concurrent two-rank `all_gather`, and the opt-in pipelined two-rank `all_reduce`.

| Three- and four-rank loopback regressions | passed in the full suites above |

## Performance review

Interleaved fresh process pairs on a direct Thunderbolt 4 link between a Linux/NVIDIA host and an Apple-silicon Mac, both orientations, against the 0.6.1 binaries.

- Two-rank `all_gather`: 25% to 66% lower completed latency in the sampled sizes; the default `all_reduce` and point-to-point paths are within measurement noise of 0.6.1.
- Opt-in pipelined `all_reduce`: lower latency from 256 KiB (see the AllReduce pipeline page for the figures and the cases to avoid).
- No reproducible regression above the noise of the measurement was found. The single-host loopback slowdown at 4 MiB and above is documented in the changelog.
- Interface error counters and drops did not change during the runs. PCIe AER reporting was unavailable on the Linux host, so nothing is claimed about PCIe errors.

## Release-candidate artifacts

The CI-built archives of 0.7.0rc1 were installed on both hosts, with their checksums, SBOMs and build attestations verified, and exercised on the physical link.

| Check | Result |
|---|---|
| C and C++ consumers of each archive (Linux host, Linux CUDA, macOS) | passed |
| Public-API tests built against each archive's static library | passed (Linux 29, CUDA 3 tests with and without staged chunking, macOS 29) |
| Mixed versions, 0.6.1 and the candidate archives, both orientations, pipeline on either side | 8 of 8 combinations passed |
| Native `all_gather`, candidate against 0.6.1, interleaved | 29% to 59% lower; `all_reduce` and large point-to-point within noise |

`src/` and `include/` of the release are identical to the tree whose sanitizer and CTest results are listed above; the sanitizer and CTest runs were not repeated.

## Adapters

The adapter release candidates (torch-tbccl 0.3.0rc1, vllm-tbccl 0.3.0rc1, exo-tbccl 0.4.0rc1) were built by CI against 0.7.0rc1 and run on the same pair of hosts with the loaded library verified: PyTorch collectives and DDP were correct with the default `all_gather` faster and the default `all_reduce` within noise; the Exo canary produced identical tokens and an unchanged default step time; vLLM with CUDA and Apple Metal passed its validation client (short, concurrent and cancel phases) in both orientations. The adapter pages record the details.

## Known limitations of this validation

- All measurements come from one Linux CUDA / Apple Metal machine pair. During this validation the link showed elevated TCP retransmissions with no interface errors or drops; an intermittent delay of unpipelined 16 MiB device collectives was seen with the 0.6.x and 0.7 libraries alike.
- PCIe AER reporting was unavailable on the Linux host (`pci=noaer`); no statement about PCIe errors is made.
